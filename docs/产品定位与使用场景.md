# 产品定位与使用场景

更新：2026-11-27。适用于电脑 A、电脑 B 及后续参与本项目的开发者。

## 1. 开发前先回答的问题

用户明确要求：做这个模拟器时，必须持续思考服务的人群是谁，这些人可能在什么情况下、如何使用。每次决定需求、交互、数据与优先级时，都要回到这个问题。

当前开发工作围绕“用手边食材安排下一顿饭”展开：选食材 → 找能做的菜 → 组成一桌 → 核对缺料 → 查看做法。新增模块应解释它怎样帮助这条流程，而不是仅因能实现或看起来丰富就加入。

## 2. 已确定的方向与尚待验证的假设

已确定的用户要求：

- 关注真实使用人群、情境和操作方式，并让这些判断影响功能取舍。
- 页面水墨风；食材与菜品正常配色，可以复用许可适用的现成图案。
- 图片与文字必须对应，不能用鸡腿图代替鸡翅中；原谱照片、主料示意和熟制参考应明确区分。
- 持续考察 GitHub 可复用内容，核对内容与许可后采用，减少不必要的自建。
- 两台电脑通过 GitHub 协作，A 负责页面、整合与发布，B 负责内容、素材和计算逻辑。

当前产品假设：优先服务“想用手边食材解决下一顿饭，但不知道做什么、怎么搭配”的家庭做饭者。他们可能会做少量菜，但经常需要选菜与搭配帮助。下班回家、打开冰箱、准备买菜、厨房中查看做法，都是候选情境。

这些人群和情境是项目中的设计假设，尚无访谈、问卷或使用日志支持，不能写成“用户大概率如此”的已验证结论。当前没有依据限定用户年龄、职业、家庭规模，也没有证明节省多少时间。后续用真实使用过程验证或修正。

## 3. 情境、问题与产品响应

| 候选情境 | 当时想解决的问题 | 应提供的帮助 |
| --- | --- | --- |
| 回家打开冰箱 | 有鸡蛋、番茄和半颗包菜，能做什么？ | 少量操作选择手边食材，直接找到能做或只缺少量材料的菜 |
| 准备买菜 | 家里已有一些东西，再买什么能凑一顿？ | 明确展示差什么，合并整桌采购项；后续评估补一种材料能增加哪些选择 |
| 已选好几道菜 | 缺料有没有重复，搭配是否符合自己的意愿？ | 汇总主要食材与缺料，支持调整菜品；不能未经依据宣称营养均衡 |
| 手机放在厨房 | 下一步怎么做、材料用多少？ | 做法入口直接，原谱用量和步骤清楚，减少来回翻找 |

第一种情境作为当前主入口。关系图用于辅助探索，用户不应必须研究关系图才能得到能做什么的答案。

## 4. 当前阶段的功能取舍

优先：

1. 把“能做什么”回答清楚：材料齐全、只差一种与缺较多材料的菜容易区分，说明匹配依据。
2. “今日一桌”围绕下一顿饭：方便选入/移出菜品、查看逐道缺料、汇总整桌缺料、打开做法。
3. 缺料按种类去重，并注明哪些菜需要它；已有必需材料、缺少必需材料与原谱可选材料分清。
4. 支持导出实际可用的备料清单；选料或菜单变化后，汇总随之更新。
5. 保留水墨风，但关键信息清楚、操作顺手。避免过浅文字、小字号、装饰占据关键操作区域及频繁弹窗。

暂缓：独立的复杂菜单管理、中国地图、自动平替、账号同步与未经核实的用量计算。此处是当前排序，不表示永不实现。现有关系图保留，不抢占核心流程。

人数换算需先明确原谱份量、数量、单位、调味料和离散食材的处理规则；B 核实并提供计算依据，A 再接入界面。不能先做人数按钮再输出无依据的克重。材料种类齐全不等于数量、锅具、技能或营养条件均满足。

## 5. “模拟器”名称与当前实现边界

当前实现更接近选菜与备餐工具，尚不具备切菜、火候、调味或烹饪结果变化的模拟。不能将未实现的烹饪模拟写成现有能力。

是否加入真实烹饪模拟，需要另行明确用户目标与核心交互。现阶段先让“现有食材安排一顿饭”完整可用；本文件不擅自决定永久取消模拟方向或更改产品名称。

## 6. 贯穿设计与验收的任务

教学/验收情境：家里有番茄、鸡蛋和包菜，想安排下一顿饭；看看能做哪些菜，选好后知道还要准备什么，并能直接查看做法。

这是构造的使用情境，不是真实用户研究记录。也不预设这三种材料就能做成所有对应菜谱；常备调料、原谱必需材料仍须按实际数据核对。

验收时检查：

- 能否理解并选中已有食材，常备调料是否清楚且可调整？
- 能否看懂能做、只缺少量材料与缺较多材料的区别？
- 选好菜后，能否追溯每个缺料对应哪些菜，并调整这一桌？
- 同一缺料是否只列一次，可选项是否会被误当必购项？
- 食材选择或菜单变化后，结果和导出是否保持一致？
- 做法入口是否直接，原谱份量、步骤和版本说明是否可读？
- 手机使用时，文字、图片和控件是否妨碍完成任务？

不预设通过所需的秒数或点击阈值。先记录实际操作步骤、误解和中断位置，之后再确定有依据的优化目标。

## 7. A、B 如何落地

| 电脑 | 最近任务 | 对共同目标的贡献 |
| --- | --- | --- |
| A | 完善今日一桌、逐道缺料、整桌清单与手机做法入口 | 让下一顿饭的选择与准备过程连贯 |
| B | 先核对现有图文和材料标注，再补准确素材与来源记录 | 避免用户被错误图片、材料或匹配结果误导 |
| A + B | B 整理份量/单位和计算规则，双方确定字段后由 A 接界面 | 让以后的人数换算有依据且可解释 |

仍遵守 docs/双电脑协作.md 的文件边界与 PR 流程。本文定义方向和验收问题，不代表上述功能已经全部完成。

## 8. 后续需求与交接的简短说明

每项新增功能或较大改动，在任务说明或 PR 中写清：

1. 帮助谁、在什么情境下完成什么任务？这是已观察到的问题还是待验证假设？
2. 当前哪里不顺畅，改后具体少了什么困惑或操作？
3. 用哪个实际流程验证，有哪些未实现内容与证据边界？

遇到使用证据与当前假设矛盾时，记录依据并调整定位或设计。不能为了维护既有方案忽略实际问题，也不把 AI 的推测当作用户研究。
